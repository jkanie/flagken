# flagken

Self-hosted feature flags. Flags carry targeting rules, % rollouts, kill switches, a separate state in each environment (development, staging, production). Every change lands in an audit log and reaches running apps (in under 1 second in the tests) and open consoles. A TypeScript SDK evaluates flags in Node.js services and in browsers, and keeps working from its last snapshot when the server is away.

The name: "ken" is the range of what you know (Old English _cennan_, to make known), so flagken is knowing which flags are on, for whom.

## What it does

- **Flags of 4 kinds:** boolean, string, number, JSON. Each flag has 2 to 20 variations.
- **Targeting per environment:** individual context keys, rules with attribute conditions (`in`, `contains`, `startsWith`, `endsWith`, `lt`, `lte`, `gt`, `gte`, `before`, `after`, each one negatable), then a default rule. Rules run top to bottom and the first full match decides.
- **% rollouts:** any rule or the default rule can split users over variations in steps of 0.01%. When the share of 1 variation grows in a 2-way split, users already on it stay on it.
- **Kill switch:** 1 call serves the off variation to everyone in an environment. It needs no `If-Match`, so a stale page never blocks it in an incident. It keeps the rules, so turning it off restores them as they were.
- **Scheduled changes:** turn a flag on or off, or set a new default rollout, at a set time (BullMQ delayed jobs).
- **Live push:** SDKs get changes over Server-Sent Events. Consoles get them over a WebSocket. Changes cross server instances through Redis publish and subscribe.
- **Audit log:** who, when, which environment, the JSON before the change, the JSON after it. The console shows it as a diff.
- **Signed webhooks:** HMAC-SHA256 with a timestamp, retries with exponential back-off, a delivery log, an SSRF guard on every target.
- **Edit conflicts:** every flag and every flag state has an ETag. A save with an old `If-Match` gets 412, a save without one gets 428.
- **Roles and keys:** each console user has 1 of 3 roles: owner, editor, viewer. Each environment has server keys (read flag rules) and client keys (read evaluated values only).
- **Operations:** health checks, Prometheus metrics, OpenTelemetry tracing that sends nothing unless an endpoint is set, rate limits, security headers, a clean shutdown.
- **Console (Vue 3):** flag list with search, flag editor, environments with their API keys, webhooks with a delivery log, audit log with diffs, users. It updates live when someone else changes a flag. Axe reports 0 violations on every page at desktop and phone width.

## How it fits together

```
  browser console (Vue 3, Pinia)            your services and web apps
        |   HTTP (cookie session)                  |   @flagken/sdk
        |   WebSocket /ws  <-- live events         |   HTTP + Server-Sent Events /sdk/v1/stream
        v                                          v
  +-------------------------------------------------------------+
  |  apps/server (NestJS 12 on Express 5), N instances           |
  |                                                              |
  |  guards: throttler (Redis) -> session or API key -> role     |
  |  controllers: auth, users, projects, flags, schedules,       |
  |               webhooks, audit, sdk, health, metrics          |
  |  flag change + audit_log + outbox row: 1 transaction         |
  |  OutboxRelay -> ChangeBus + webhooks queue                   |
  |  ChangeBus (Redis pub/sub) -> LiveService -> SSE and WS      |
  |  BullMQ workers: scheduled changes, webhook delivery         |
  +----------------+----------------------------+----------------+
                   |                            |
            PostgreSQL 17                    Redis 8
     flags, states, users, keys,     pub/sub channel, BullMQ queues,
     audit log, outbox, webhooks,    rate-limit counters
     schedules

  packages/shared      types, rules engine, MurmurHash3 bucketing, JSON diff
                       (used by the server, the SDK, the console)
  packages/api-client  OpenAPI document + types generated by openapi-typescript
                       (used by the console and the SDK)
  packages/sdk         Node.js and browser SDK
```

A flag change flows like this: in 1 transaction, the flag service writes 3 rows: the new state with a version check, the audit entry with the old state and the new one, an outbox row that holds the events to send (`flag.changed`, `audit.created`). After the commit, the outbox relay publishes those events on the Redis channel, queues 1 webhook job per matching endpoint, then marks the row sent. Every instance, the sender included, gets each message and passes it to its own SSE streams and console sockets. So a change never commits without its audit entry, and an entry never without its events.

### Server-Sent Events for SDKs, a WebSocket for the console

| Channel                   | Used by                       | Why                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| SSE, `GET /sdk/v1/stream` | SDKs in services and browsers | Traffic goes 1 way, server to app. SSE is plain HTTP, so it passes proxies and load balancers that handle HTTP. It carries the API key in a normal `Authorization` header. The SDK reads it with `fetch`, so the same code runs in Node.js and browsers. The stream starts with a `put` of every flag, then sends `patch` and `delete` events, plus a `ping` every 15 seconds. |
| WebSocket, `/ws`          | the console                   | The console talks back: it signs in with the session cookie of the handshake, then subscribes to a project. The server checks the `Origin` header of the handshake, so another site cannot open a socket with a user's cookie.                                                                                                                                                 |

## Why these choices

- **Kysely over Prisma, Drizzle, TypeORM.** Kysely is a typed query builder with no engine binaries and no code generation step, so the server builds and runs the same in CI, in Docker, on a laptop. Queries stay plain SQL, which matters for the 2 places that carry the edit-conflict logic (`UPDATE ... WHERE version = $expected RETURNING *` and `SELECT ... FOR UPDATE`). Migrations live in TypeScript, so the built server carries them. Prisma was not tried here. Its npm `latest` tag pointed at a release candidate (8.0.0-rc.33) on 2026-11-09.
- **MurmurHash3 for bucketing.** The bucket of a user is `murmur3_x86_32(utf8("<flag key>:<user key>"), seed 0) mod 10000`. MurmurHash3 is fast, spreads keys evenly, fits in 1 short function of integer maths in `packages/shared`, has published reference values, so the server, the Node SDK, the browser SDK compute the same bucket without a crypto library. The flag key is part of the input, so 1 user lands in unrelated buckets for different flags. Tests pin known inputs to known buckets and check the spread with chi-square tests over 100,000 and 200,000 keys. The modulo leaves a small bias: 2^32 mod 10000 = 7296, so buckets 0 to 7,295 each get 1 hash value more out of 429,496, a difference of 0.00023%.
- **1 delivery path through Redis.** The instance that saves a change does not push to its own clients directly. It publishes, and every instance (itself included) delivers what arrives from Redis. 1 path means a client on instance B sees exactly what a client on instance A sees.
- **Audit outbox for flags.** A flag change writes its audit entry and an outbox row in its own transaction, with the actor and the request id that the `AuditInterceptor` puts in an AsyncLocalStorage store. A refused change writes nothing. The `OutboxRelay` sends unsent rows in id order after each change and every 5 seconds. A row whose sending fails (Redis down, say) stays with its error, and the rows after it wait, so events never pass each other. `FOR UPDATE SKIP LOCKED` lets several instances share the work. Delivery is at least once: a row that failed half-way publishes its messages again, which SDKs and consoles ignore by version, and webhook jobs are keyed by event, so a webhook is queued once. A scheduled change runs the same path with a system actor.
- **Audit by interceptor for the rest.** Changes to users, projects, keys, webhooks, schedules record what changed in the same store, and the `AuditInterceptor` stores those entries with the actor, the time, the request id after the handler succeeds.
- **Rules evaluated in 1 shared function.** `evaluateFlag` in `packages/shared` runs in the server (for client keys) and in the SDK (for server keys). The console checks rules with the same validation functions as the server. An integration test compares server and SDK answers for 500 contexts.
- **Client keys never see rules.** Anyone can read a client key in a browser, so the server evaluates for the browser's context and sends only values. Server keys get the rules for local evaluation, which keeps service latency at memory speed.
- **Cookie sessions.** The console session is an HttpOnly, SameSite=Strict cookie holding a signed JWT. The role is read from the database on each request, so a demotion takes effect at once. Bodies must be JSON (no form parser), so a cross-site HTML form cannot post to the API.

## Set-up

You need Node.js 26.13 or later, pnpm 12, Docker (for PostgreSQL and Redis, also for the integration tests).

```bash
git clone https://github.com/jkanie/flagken.git
cd flagken
pnpm install
docker compose up -d --wait          # PostgreSQL 17 on 5432, Redis 8 on 6379, bound to 127.0.0.1
cp .env.example .env                 # then fill in the values below
pnpm build
```

For local work, these values in `.env` match `compose.yaml` (made-up local values, not secrets):

```bash
DATABASE_URL=postgres://flagken:flagken-local-only@127.0.0.1:5432/flagken
REDIS_URL=redis://127.0.0.1:6379
SESSION_SECRET=replace-with-32-or-more-random-characters
COOKIE_SECURE=false
NODE_ENV=development
```

Create the first owner (there is no public sign-up), add the made-up demo data, start the server and the console:

```bash
ADMIN_EMAIL=owner@example.com ADMIN_PASSWORD='choose-12-or-more-chars' pnpm --filter @flagken/server cli create-admin
pnpm --filter @flagken/server cli seed      # prints 1 server key and 1 client key for development, once
pnpm dev:server                             # http://localhost:3000, API docs at /docs
pnpm dev:console                            # http://localhost:5173, proxies /api, /sdk, /ws to :3000
```

In production the server serves the built console itself: set `CONSOLE_DIR` to `apps/console/dist` (the Docker image does this). The console and the API then share 1 origin.

Docker:

```bash
docker build -t flagken .
docker run --env-file .env -p 3000:3000 flagken
```

Inside the container, `127.0.0.1` is the container itself, so point `DATABASE_URL` and `REDIS_URL` at hosts the container can reach.

The server applies database migrations on start. `node dist/cli.js migrate` applies them on their own, for deployments that turn `MIGRATE_ON_START` off.

| `GET /api/v1/projects/{project}/audit`                                            | viewer                  | Audit entries, filtered by `environment` and `flag`, paged with `before`.                                                            |
| `GET /sdk/v1/flags`                                                               | server key              | Every flag with its rules.                                                                                                           |
| `POST /sdk/v1/evaluate`                                                           | client key              | Values for 1 context.                                                                                                                |

Error codes worth knowing: 401 (no session or key), 403 (role or key kind too low), 409 (key already used, or flag archived), 412 (stale `If-Match`), 422 (rules that do not fit the flag, with every problem listed), 428 (`If-Match` missing), 429 (rate limit).

## SDK usage

The SDK lives in `packages/sdk` (published to npm later, see the roadmap). It is written for Node.js and browsers (`fetch`, Web Streams, Web Crypto). The tests run it in Node.js 26.13. A run inside a browser is not tested yet.

Server side, with a server key: the SDK holds the rules and evaluates in memory.

```ts
import { createFlagkenClient } from '@flagken/sdk'
import { fileStore } from '@flagken/sdk/node'

const flags = createFlagkenClient({
  baseUrl: 'https://flags.example.com',
  apiKey: process.env.FLAGKEN_SERVER_KEY!, // fk_srv_...
  store: fileStore('/var/cache/my-service/flags.json'), // optional: start from the last snapshot when the server is down
})
await flags.start() // resolves on the first data, or after 5 seconds with the snapshot

if (flags.variation('new-checkout', false, { key: 'u_7f3a9c', country: 'CA', plan: 'beta' })) {
  // new checkout
}
flags.on('change', ({ key }) => console.log(`flag ${key} changed`))
// Or follow 1 flag: called only when its value for this context changes. stop() ends the calls.
const stop = flags.watch('new-checkout', false, (on) => console.log(`new checkout ${on ? 'on' : 'off'}`), { key: 'u_7f3a9c' })
// Every flag's value for 1 context in 1 object, such as for a page that the server renders.
const values = flags.allValues({ key: 'u_7f3a9c' })
```

In a browser, with a client key: the server evaluates for 1 context and sends values only.

```ts
import { createFlagkenClient, localStorageStore } from '@flagken/sdk'

const flags = createFlagkenClient({
  baseUrl: 'https://flags.example.com',
  apiKey: 'fk_cli_...', // client keys are safe to ship to browsers: they read values, never rules
  context: { key: 'u_7f3a9c', country: 'CA' }, // an opaque id, never a name or e-mail address
  store: localStorageStore(),
})
await flags.start()
const ranking = flags.variation('search-ranking', 'classic')
await flags.identify({ key: 'u_b41e07' }) // another user signs in
```

What the SDK does on its own:

- Reconnects with exponential back-off (1 second up to 30 seconds, half of each wait random) when the stream drops. It also reconnects when the stream stays silent for 45 seconds.
- Keeps serving the last known flags while offline. The snapshot store keeps them in memory by default. A file store (Node.js) and a `localStorage` store (browser) keep them across restarts. Writes to a file go through a temporary file and a rename.
- Ignores a patch older than what it holds, so events that arrive late cannot roll a flag back.
- Returns the fallback when a flag is missing or has another type than the fallback, with the reason in `variationDetail`.
- `streaming: false` polls `GET /sdk/v1/flags` or `POST /sdk/v1/evaluate` through the generated API client instead of streaming.

Checking a webhook on the receiving side:

```ts
import { verifyWebhookSignature } from '@flagken/sdk'

const ok = await verifyWebhookSignature({
  secret: process.env.FLAGKEN_WEBHOOK_SECRET!, // whsec_...
  body: rawBody, // the exact bytes received, before JSON parsing
  header: request.headers['flagken-signature'],
}) // false for a changed body, another secret, a timestamp more than 300 seconds off
```

## Safety and privacy

- **Passwords:** Argon2id with 19 MiB memory, 2 passes, 1 lane. A sign-in with an unknown e-mail address still checks a hash, so both cases take the same time and give the same message. Sign-in has its own rate limit.
- **Sessions:** HttpOnly, SameSite=Strict, `Secure` by default, signed with `SESSION_SECRET`. The server checks the issuer and the audience of each token. Disabled users are refused on their next request.
- **API keys:** 32 random bytes. The database keeps a SHA-256 hash and a 14-character prefix for display. The audit log names keys by prefix only.
- **Webhook targets:** only `http` and `https`, no user name or password in the URL. Private (RFC 1918), loopback, link-local (cloud metadata at 169.254.169.254 included), shared, multicast, documentation, reserved ranges are refused for IPv4 and IPv6, as are IPv4-mapped, IPv4-compatible, NAT64, 6to4 forms of those addresses. The check runs when the URL is saved. It runs again on the address the socket connects to, so a DNS answer that changes later is caught, then again on every redirect (at most 3). A blocked delivery is not retried. `ALLOW_PRIVATE_TARGETS` turns the check off for local work.
- **Webhook signatures:** `Flagken-Signature: t=<unix seconds>,v1=<HMAC-SHA256 hex of "<t>.<body>">`. Each attempt is signed again with a fresh timestamp, so receivers can refuse anything older than 5 minutes. The secret is shown once and never appears in the audit log or in lists.
- **HTTP:** helmet headers (CSP with `default-src 'self'` and `frame-ancestors 'none'`, HSTS, `nosniff`), CORS only for `CORS_ORIGINS`, JSON bodies only with a 256 kB limit, an `Origin` check on the console socket, a request id on every response.
- **Tracing:** without `OTEL_EXPORTER_OTLP_ENDPOINT` the OpenTelemetry SDK is not started, so no trace data leaves the server. A test checks both cases.
- **What is stored about end users:** nothing the SDK does not send. Client keys send the context in a header, not in the URL, so it stays out of access logs. The SDK's offline snapshot holds a hash of the context, not the context. Flag targets hold whatever context keys an editor types. Use opaque ids, as the demo data does.
- **Sample data:** the seed makes up a "Demo Shop" project and opaque context keys such as `u_7f3a9c`. It holds no real people and no personal data.

## Known limits

- Only flag changes go through the outbox. Changes to users, projects, keys, webhooks, schedules still write their audit entry after the change commits, in a second statement.
- Server keys get every rule, so a service holding one sees context keys listed in targets. Treat server keys as secrets.
- Rate limits count per client IP. Behind a proxy, set `TRUST_PROXY` or every client shares 1 limit.
- Webhook signing secrets are stored as plain text, because the server needs them to sign. Database access means access to them. There is no rotation endpoint yet.
- Evaluation metrics count evaluations the server makes for client keys. Server-key SDKs evaluate locally and report nothing back.
- 1 project's flags list returns at most 500 flags, with no paging yet.
- Not built yet: segments (reusable lists of users), experiments, single sign-on, approvals for changes. See `ROADMAP.md`.
- CI does not build the Docker image. It was built and started by hand: the server answered `/health/ready`, served the console, ran as the `node` user. That build ran behind a proxy with its own certificate, added in a copy of the Dockerfile with 2 extra lines. The committed Dockerfile was not built on a network without that proxy.
- `pnpm-workspace.yaml` holds a `minimumReleaseAgeExclude` list. pnpm 12 wrote it during install, because the newest versions picked for this seed are younger than pnpm's minimum release age setting. `allowBuilds` in the same file lets 2 packages run install scripts (`@swc/core`, `msgpackr-extract`) and denies the rest.
